# 源可用性与质量专题研究

> 对应纲领 `产品主旨与开发方向.md` 第三节原则 5（工程预算投在成功率）与第二节北极星指标。
> **本文只记录可复现的事实与结论**：实测数据标日期，推断标"待验证"。

---

## 一、为什么这是第一课题

这个 App 的唯一内容来源是公开 IPTV 聚合源。它决定了三件事的天花板：

- 用户能不能看到想看的台（覆盖）
- 看到时是不是在转圈（可用性）
- 画面清不清、卡不卡（质量）

功能代码写得再好，源不行就是黑屏。所以**源的研究优先级高于任何 UI 与功能改进**。

---

## 二、先把"源质量"定义清楚

"源好不好"不是一个指标，是**六层依次通过的漏斗**。任何一层不过，用户看到的就是"播不了"：

| 层 | 含义 | 当前是否度量 | 失败时用户看到 |
|---|---|---|---|
| L0 可拉取 | 订阅地址能下载、体积合理 | 部分（无耗时/吞吐度量） | 频道列表空 |
| L1 可解析 | 格式正确、频道数合理 | 是（`parseInto`） | 频道少一半 |
| L2 可去噪 | 白名单/垃圾/点播/黑名单域名过滤 | 是（`applyChannelFilter`） | 看到斗鱼/购物台 |
| L3 可探活 | 连接能建立、首包有响应 | 是（`ChannelProbe`） | "暂不可用"标记 |
| **L4 可播放** | **playlist 有效 + 首个分片可下载** | **否（最大缺口）** | 一直转圈 → 终态 |
| L5 可稳定播放 | 连续播放无卡顿、断流能恢复 | 部分（`rebufferTimes`） | 播放中突然卡住 |
| L6 画质达标 | 真实分辨率/码率 | 否（靠名字猜） | 画面糊 |

**核心结论**：现在度量了 L0~L3，而用户感知最强的 **L4/L5/L6 基本没度量**。这是"源可用性与质量"研究的主战场。

## 三、实测数据快照（2026-09-13，本机网络）

### 3.1 源连通性（6 个候选源）

| 源 | 状态 | 体积 | 耗时 | 评价 |
|---|---|---|---|---|
| Guovin（raw） | 200 | 396 KB | 2.55s | 正常 |
| Guovin（jsdelivr） | 200 | 396 KB | 2.23s | 略快于 raw |
| BigBigGrandG | 200 | 330 KB | 2.22s | 正常 |
| **suxuang** | 200 | 97 KB | **25.0s（超时上限）** | **慢源，会拖满整体截止** |
| zbds.top | 200 | 120 KB | 2.33s | 正常 |
| iptv-org/cn | 200 | 29 KB | 0.89s | 快但覆盖小 |

**源抖动**：`BigBigGrandG` 在另一次抓取中返回 **0 行**（同一 URL）。源不是"要么好要么坏"，是**概率可用**。

### 3.2 内容规模与重复度（4 个源合并）

| 指标 | 数值 | 说明 |
|---|---|---|
| 频道线路总数 | 4246 | 4 源合并后的原始条目 |
| 唯一 URL | 3900 | **346 条跨源重复（8.1%）** |
| 唯一频道名 | 2791 | 归一化前 |
| 单频道最大线路数 | **12** | 深圳卫视 / CCTV15 / 新疆卫视 |
| CCTV5+ / CCTV5 / 山东体育 | 11 | 典型：热门台线路多 |

推算：白名单过滤后约 **79 台 × 平均 10 条 ≈ 800 条线路**。

### 3.3 线路的"真实多样性"（关键）

| 指标 | 数值 |
|---|---|
| 唯一 host | **644**（承载 4246 条，平均 6.6 条/host） |
| 裸 IP 线路 | **580 条（13.7%）** |
| 唯一 IP | 106 |
| top IP 段聚集 | 8 个 /16 段占 **364 条**（占全部 IP 线路的 63%） |

**结论：线路数量 ≠ 线路多样性**。12 条线路很可能只对应 3~4 台真实服务器。

### 3.4 端到端实测：CCTV-1 的 8 条线路

对 8 条 CCTV/CCTV-2 线路做完整链路测量：

| # | 入口 | 总耗时 | connect | 重定向次数 | 最终 |
|---|---|---|---|---|---|
| 1 | 63.141.230.178:82 | 2.57s | 1.76s | **4** | 200 m3u8 |
| 2 | 38.75.136.137:98 | 1.04s | 0.53s | 1 | 200 m3u8 |
| 3 | 204.12.221.218:8181 | 0.99s | 0.50s | 1 | 200 m3u8 |
| 4 | 74.91.26.218:82 | 2.00s | 1.49s | 1 | 200 m3u8 |
| 5 | 198.204.228.26 | 1.03s | 0.49s | 1 | 200 m3u8 |
| 6 | bztv.tvbus.cc:8081 | 0.98s | 0.33s | 1 | 200 m3u8 |
| 7 | 198.204.228.26 | 1.01s | 0.49s | 1 | 200 m3u8 |
| 8 | 204.12.221.218:8181 | 0.94s | 0.45s | 1 | 200 m3u8 |

**发现的链路结构**：

1. 全部是 **302 跳转**：入口 URL → 302（带时效签名）→ 真实流。
2. 302 目标带签名：`?t=<时间戳>&k=<md5>`、`?jsbt=<ts>&jsbk=<md5>`、`?u=<客户端IP>&a=<节点>`。
3. **入口 URL 长期有效**：再次请求同一入口仍 200（服务端每次重新签名）。所以**缓存入口 URL 是安全的**，签名的短时效不构成问题。
4. 最终内容是**有效的 media playlist**：
   ```
   #EXTM3U
   #EXT-X-VERSION:3
   #EXT-X-TARGETDURATION:10
   #EXT-X-MEDIA-SEQUENCE:10728
   #EXTINF:10.000000,
   cctv1md/segment_10728.ts
   ```
5. **8 条入口最终汇聚到 3~4 台真实服务器**（`204.12.241.18`、`204.12.234.154`、`63.141.239.226`、`74.91.26.218`）——**伪多样性被实测证实**。
6. **重定向次数不稳定**：同一条入口两次请求分别是 2 次与 4 次（GSLB 调度结果不同）。

## 四、诊断（按影响排序）

### D1 【高】探活判据与用户目标不一致

`ChannelProbe.probe()` 只判：`isSuccessful || 206 || 3xx || 405`。

问题：
- 判"可达"不等于判"可播"。播放需要 playlist 有效 + 首个分片可取（L4），当前完全不校验。
- 反过来，**探活会把好线路误判为失败**：`connectTimeout=2500ms`，而实测跨洲 connect 达 **1.76s**，重定向 1~4 次；弱网/高峰期极易超时 → 好线路被标"探测失败"并排到末位。

> 实测已证明这些线路**是真能播的**，所以"误判为失败"比"漏判"更值得警惕。

### D2 【高】首帧成本没有被度量

排序用的是"探测首包延迟"，但真实起播成本 =
`N 次 302 连接 + playlist 下载 + 首个分片下载`。实测重定向 1~4 次，单次 connect 0.33~1.76s。
**结论**：应该记录**端到端拿到首个分片的耗时**，而不是首包延迟。

### D3 【高】慢源拖垮每次冷启动

`fetchAll` 的整体截止是 12s，`latch.await(15s)`。而 `suxuang` 实测 25s。
`fetch` 的 `readTimeout=6s` 是"两次读之间"的超时，**持续慢速传输不会触发**。
→ 有慢源时，每次冷启动都要白等到 12s 截止，与"秒开"目标直接冲突。

### D4 【中】画质靠名字猜

`TVList.qualityScore()` 从频道名/URL 匹配 `4K/1080/FHD/720`。
- 折叠后同名频道的各线路**命名相同** → 画质分全部相同 → 排序退化为只看延迟。
- 源里命名虚标常见。
- 实测的 playlist 是**单码率**（无 `#EXT-X-STREAM-INF`），所以分辨率只能从**分片本身**或 master playlist 获得。

### D5 【中】伪多样性导致单点故障

12 条线路汇聚到 3~4 台服务器（实测）。当前排序按延迟，会把**同一 IP 的多条线路排在一起**。
该 IP 一旦故障，前 2~3 条自动轮换线路同时失效，直接进入终态。

### D6 【中】探活覆盖面不足 + 结果新鲜度问题

- 每轮上限 200 条，实际约 800 条线路 → **至少 3/4 的线路永远"未探测"**，排序对它们退化为按画质（而画质也不准）。
- 重探间隔 10 分钟，但 `sortKey()` 读取结果时**不判新鲜度**，10 分钟前的结论会被当作当前结论。

### D7 【中】无 HTTP 缓存协商

每次启动全量下载 4×~300KB。GitHub raw 支持 `ETag`/`If-None-Match`，命中可返回 304（省流量、省时间）。
当前每个源都从头下载。

### D8 【中】每次拉源新建 OkHttpClient

`TVList.fetch()` 在镜像循环内 `OkHttpClient.Builder().build()`，连接池与 TLS 会话都无法复用。
（`EpgStore` 的同类问题已在本轮修复。）

### D9 【低】URL 级去重不彻底

跨源重复 URL 有 8.1%（实测 346/4246）。`parseInto` 里有 `if (!vm.videoUrl.contains(trimmed))` 去重，
但只在**同一折叠 key** 内生效；同名归一化后的跨源合并路径另有逻辑，需复核是否覆盖全部重复。

### D10 【低】失败记忆与 URL 的绑定不稳定

`LineHealth` 以 URL 为 key。若源更新导致 URL 变化（或签名结构改变），失败记忆与成功记录都会失配。

## 五、改进路线（按 ROI 排序）

### P0（直接提升可播率与秒开）

| # | 动作 | 预期收益 | 验证方法 |
|---|---|---|---|
| P0-1 | **单源超时 + 慢源隔离**：单源总时长上限（如 6s），超时即丢弃该源；并记录每源耗时 | 冷启动不再被慢源拖到 12s | 日志中 `remote sources merged` 耗时；构造包含 suxuang 的配置对比 |
| P0-2 | **探活升级为 L4 两段式**：GET playlist → 校验含 `#EXTM3U` → 取首个分片（HEAD/Range）→ 记录 `endToEndMs` | 排名第一的线路"点开就能看" | 抽 20 条线路，对比探活结论与实际播放 |
| P0-3 | **放宽探活超时**（connect 2500→4000ms，整链超时 8~10s），避免误杀跨洲好线路 | 减少好线路被误标"失败" | 同一批线路改造前后 `ok` 比例 |
| P0-4 | **复用 OkHttpClient**（`TVList`/`Utils`）+ **ETag 协商** | 降低重复握手与重复下载 | 第二次启动的下载体积（应接近 0） |
| P0-5 | **排序改用端到端耗时**（替代首包延迟） | 起播更快 | 首帧时间 p50/p90 |

### P1（提升长期质量）

| # | 动作 | 预期收益 |
|---|---|---|
| P1-1 | **按 /16 IP 段聚类去重**，每频道保留 top N（如 6 条，且不同网段优先） | 消除伪多样性，单点故障不再一次打掉整批 |
| P1-2 | **统一"线路档案"模型**：`LineProfile(url){quality, resolution, probeOk, endToEndMs, successCount, failCount, lastError, updatedAt}` 单文件落盘 | 替代现在分散在 `urlQuality`/`ChannelProbe`/`LineHealth` 的三份数据 |
| P1-3 | **源健康统计与导出**：每源的成功率、频道数、线路可达率、耗时；暴露到远程配置页 | 用数据决定"留哪个源"，而不是凭感觉 |
| P1-4 | **真实画质探测**：从 master playlist 的 `RESOLUTION/BANDWIDTH`，或首个分片实测 | 排序从"猜"变"测" |
| P1-5 | **探活结果带时效**：`sortKey` 忽略过期结论 | 避免用 10 分钟前的状态做决策 |

### P2（进阶）

>
> **F1（已修复）**：排序与打散原先只在加载时（`TVList.finalize`）执行一次，导致首次安装时拿不到探活结论。
>
> 现改为**运行时动态重排**：`TVList.sortLines(tv, trim)` 抽成公共入口，`TVViewModel.resortLines()`

> 两条安全约束：运行时 `trim = false`（不裁掉正在播放的线路）、`videoIndex` 跟随当前地址（播放不中断）。
>
> 实测：探活完成与重排日志相隔 **1ms**（`probed 200/200` → `resort lines: CCTV-2 -> 6 lines, now playing #1`）。

## 六、可复用的测量方法

以下命令在 Windows PowerShell 下可直接跑（已实测可用）。

### 6.1 源连通性与吞吐

```powershell
foreach($p in @(
  @('guovin','https://cdn.jsdelivr.net/gh/Guovin/iptv-api@gd/output/result.m3u'),
  @('biggrand','https://raw.githubusercontent.com/BigBigGrandG/IPTV-URL/release/Gather.m3u'),
  @('zbds','https://live.zbds.top/tv/iptv4.m3u'),
  @('iptvorg','https://iptv-org.github.io/iptv/countries/cn.m3u'))){
  $l = curl.exe -s -m 40 $p[1]
  $e = ($l | Where-Object {$_ -like '#EXTINF*'}).Count
  "{0,-9} lines={1,-6} extinf={2}" -f $p[0], $l.Count, $e
}
```

```powershell
# 收集 url 与 name 后：

  -w "%{time_total}s | %{time_connect}s connect | %{http_code} | redirects=%{num_redirects}`n" $url
```

> 注意：必须带 `-L`。不带 `-L` 看到的是 302 + `text/html` + 0 字节，会误判为"不可用"。

### 6.5 建议沉淀

把以上固化为 `tools/source-audit.ps1`，输出一份 JSON 快照（每源的可用率、频道数、线路数、IP 段分布、抽样端到端耗时），
再按日期存档，就能做**长期趋势**——这是"深入研究"真正需要的基础设施。

> 应用内已有轻量版：设备上跑几次后，浏览器打开 `http://<设备IP>:34567/?token=xxxxxx` 点「源健康」，
> 即可看到每个源的成功率 / 平均耗时 / 最近频道数 / 实际命中的镜像（`/api/sources`）。

## 七、待验证的假设（别当结论用）

| # | 假设 | 怎么验证 |
|---|---|---|
| H1 | 部分 200 响应其实是错误页（`text/html`） | 抽样 50 条线路，统计 content-type 分布 |
| H2 | 白名单过滤掩盖了源的真实质量 | 关闭过滤后统计全量频道可达率，与过滤后对比 |
| H3 | `ChannelProbe` 在弱网下误判比例 | 限速环境跑同一批线路，对比 `ok` 比例 |
| H4 | 同一 /16 段的线路故障相关性高 | 观察某 IP 段故障时，排序靠前的线路是否同时失效 |
| H5 | ETag 能显著减少下载 | 对同一源连续两次请求，看第二次是否 304 |

## 八、一句话总结

现在的管线把"**能不能下载**"做到了极致，但用户要的是"**能不能看**"。
下一阶段的全部重点，应该是把度量从 L3（可达）推进到 **L4（可播）与 L5（稳定）**——
具体落地就是三件事：**两段式探活、端到端耗时排序、按网段去重**。
