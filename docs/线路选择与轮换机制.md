# 线路选择与轮换机制

> 回答三个问题：**哪条线路排在最前**（排序）、**什么条件会自动换下一条**（轮换）、**失败会被记住多久**（记忆）。
> 源码：`TVList.sortLines` / `TVViewModel` / `PlayerFragment` / `ChannelProbe` / `LineHealth`。

---

## 一、先分清三种"切换"

混用这三个词会直接导致沟通错位——代码里也是三套独立机制：

| 名称 | 换的是什么 | 谁触发 | 代码入口 |
|---|---|---|---|
| **换线路** | 同一频道的**另一条 URL** | 自动，或用户手动 | `TVViewModel.nextSource()` |
| **换源类型** | **同一个 URL**，换封装解析（HLS ↔ TS） | 自动 | `TVViewModel.nextSourceType()` |
| **换台** | 切换到**另一个频道** | 用户；线路全废后自动跳过 | `MainFragment.switchTo()` / `MainActivity` |

本文主要讲第一种。

---

## 二、频道折叠：一个频道有几条线路

多个源里的同一个频道会被折叠成一条**多线路频道**，折叠键是 `TVList.canonicalName(title)`。
折叠决定了"这个频道有哪些线路可以轮换"，所以命名归一化一旦出错，**不同频道的线路会混在一起**。

折叠步骤（按实际顺序）：

| # | 处理 | 例子 |
|---|---|---|
| 1 | 大写、全角括号转半角 | `CCTV-1（综合）` → `CCTV-1(综合)` |
| 2 | 去掉圆括号 / 方括号内容 | `CCTV-1(720p)` → `CCTV-1` |
| 3 | 去空格、统一各种连字符 | `CCTV 4K` → `CCTV4K` |
| 4 | **提取 CCTV 台号主干**（含 `+` 与 `K`/`Q` 后缀） | `CCTV-1综合` → `CCTV1`；`CCTV5+体育` → `CCTV5+` |
| 5 | **非 CCTV 才**清理画质词（超高清/高清/FHD/4K/8K…） | `东方卫视4K` → `东方卫视` |
| 6 | 兜底去掉剩余连字符 | — |

### 顺序约束（重要，别当成冗余代码删掉）

**第 4 步必须在第 5 步之前。** 对央视来说 `4K / 8K` 不是画质标签，而是频道名的一部分——
CCTV 确实有 `CCTV-4K` 与 `CCTV-8K` 两个独立频道，且源的写法五花八门：

```
CCTV 4K            （带空格）
CCTV-4K (1080p)
CCTV-8K (1080p)
CCTV-8K 超高清
```

若先按画质词把 `4K` 删掉，这四个会全部归一化成 `"CCTV"`，被折叠成**同一个频道、线路互相混杂**：
标题显示 8K，实际可能正播着 4K，自动轮换时还会在两者之间来回跳。
历史上就是这样——设备上出现过一条"6 条线路的 `CCTV-8K 超高清`"，实际是这四个频道合并的产物。

配套约束：`CCTV_KEEP` 白名单里必须同时列上 `CCTV4K` / `CCTV8K`，
否则归一化改对了、却会被白名单整台丢掉（归一化与白名单是两处独立的门）。

## 三、排序：谁排第一

自动轮换只看排序后的前几条，所以**排序决定了自动轮换能看到哪些线路**。

`TVList.sortLines(tv, trim)` 的比较链（默认"可用性优先"）：

| 序 | 依据 | 说明 |
|---|---|---|
| 1 | 录像嫌疑 + 已知坏线 | 合并成一个标记，最靠后 |
| 2 | 用户手动选过的线路 | 手动偏好优先于一切自动策略（坏线已被上一级排除） |
| 3 | 历史成功率（降序） | 无记录按 **50 中性**，不冤枉没播过的新线路 |
| 4 | 探活档位（升序） | 已验证到分片 > 仅可达 |
| 5 | 画质（降序） | **实测分辨率**优先，取不到再回退名字推断 |
| 6 | 端到端耗时（升序） | 探活实测值，不是首包延迟 |

> 远程页打开「画质优先」开关后，3/4/5 的顺序变为 **画质 → 探活档位 → 成功率**。

排序之后还有两步：

- **网段打散**（`diversifyLines`）：同一网络（裸 IP 取 /16，域名取 host）只保留一条在头部，其余延后。
  实测一个频道的 8 条入口实际只对应 4 台服务器，不打散的话前两条可能在同一台机器上，
  它一挂就把自动轮换的名额全废掉。
- **裁剪到 6 条**（`trimLines`，仅加载时）：6 条 = 自动轮换 + 手动还能切，再多只会让探活覆盖不到、
  排在后面的线路按"未探测"的中性值盲排。

## 四、什么条件会自动换线路

### 两个触发源

1. **播放器报错** —— `onPlayerError` 回调。
2. **15 秒没出画面**（看门狗）—— 这条更要紧，因为"连通但不发数据"的假活线路
   **不会产生 error 回调**，只有看门狗能发现。它只在加载期间计时，所以**播放中卡死超过 15s 同样会触发**。

### 决策：错误分两类

- **源/网络类**：连接失败、超时、HTTP 4xx/5xx、content-type 错、403 等；
- **解码/渲染类**：其余。

这个分类决定走向——**源类错误不会去试"换源类型"**，因为换封装救不回 4xx/5xx，
多试只是让用户多等几个超时周期。

| 触发 | 条件 | 结果 |
|---|---|---|
| 报错 | 解码类 + 还有候选封装 + 额度未用完 | 换源类型（**不换线路**）|
| 报错 | 多线路频道 + 额度未用完 | **换线路** |
| 报错 | 单线路频道 + 额度未用完 | 原地重试同一个 URL |
| 报错 | 额度用完（解码类、未试过软解）| 软解重建（不换线路）|
| 报错 | 额度用完 | **终态**「所有线路均不可用」|
| 15s 无画面 | 次数 < 门槛 + 多线路 | **换线路** |
| 15s 无画面 | 次数 ≥ 门槛 | **终态**「线路无响应」|

### 终态之后

进入终态会停止播放、隐藏转圈，并交给 `MainActivity.onChannelUnavailable()` 统一处理
（信息条说明 + 有上限的自动跳过）。

## 五、额度与窗口（2026-09-14 调整）

| 概念 | 值 | 说明 |
|---|---|---|
| **初始窗口** | 2 | 只在前 2 条（排序最优）内轮换 |
| **放宽规则** | 每换一次 +1 | 上限 `AUTO_LINE_LIMIT_EXPANDED = 4` |
| 报错路径上限 | 窗口 × 2 | `isAttemptExhausted()` |
| 超时路径上限 | `min(窗口, 3)` | 每次 15s，封顶 45s |

**为什么放宽**：窗口原本固定为 2，一旦前两条恰好同时是坏线（公共源里很常见），
会直接判死整台——而排序第 3、4 条可能其实能播。放宽的代价是每条线路多等一个超时周期，
所以上限收在 4 条。

**超时路径的时序**（每条线路各给一次超时机会）：

| 事件 | 窗口 | 超时计数 | 结果 |
|---|---|---|---|
| 第 1 条 15s 无画面 | 2 | 1 | 换到第 2 条 |
| 第 2 条 15s 无画面 | 3 | 2 | 换到第 3 条 |
| 第 3 条 15s 无画面 | 4 | 3 | **终态**（约 45s）|

> 门槛封顶 3 次：不能让用户为了"试第 4 条"再多干等 15 秒。

**用户手动选到窗口之外时，窗口放开到全部线路**——手动选择优先于自动策略。
注意窗口放宽后自动换线自身也会走到第 3 条，所以判断"是否在窗口外"必须用**动态窗口**比较，
不能用常量（否则会把自动换线误认成手动选择）。

### 额度何时清零

- **切台**时（频道 id 变化）
- **播放成功**时

所以只要播成功过，就重新有额度。

## 六、失败会被记住多久

| 记录 | 规则 | 影响 |
|---|---|---|
| `LineHealth` 失败 | 同一条线路放弃 **2 次**，判为坏线 | 2 小时冷却期内排序垫底、可触发"暂不可用"标记 |
| `LineHealth` 成功 | 清空失败计数 + 累计成功次数 | 提高 `successRank`，下次排更前 |
| `ChannelProbe` 探活 | 同一线路 **10 分钟**内不重复探 | 浏览分组时来回切不会反复发请求 |
| `ChannelProbe` 过期 | 记录 **7 天**后丢弃 | 避免文件无限增长 |
| 用户手动偏好 | 最多 **100** 条频道 | 超出淘汰最旧的 |

**换线路本身不会触发重排**：`resortLines()` 只在**探活完成**与**播放成功**时调用。
所以换线走的是 `index = (index + 1) % 窗口` 这个机械循环。

## 八、已知取舍

1. **窗口放宽 = 最坏多等 15 秒**（超时路径封顶 45s）。
   换来的是"前两条同时坏时还能试第 3 条"。若实测发现 45s 仍然偏久，应下调 `TIMEOUT_LIMIT_MAX`。
2. **自动轮换走的是死循环，不是"重新择优"**。若前两条都坏，期间不会回头重新排序
   （依赖 `recordFail` 影响的是**下一次**排序）。
3. **看门狗 15s 在弱网下仍有误杀空间**。已由两段式探活（排除取不到分片的线路）与
   连接预热（握手提前做掉）降低概率，但真机弱网下仍需实测确认。
