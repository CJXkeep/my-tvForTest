## 二、逐项验证

### V1 凤凰台仍可播（trust-all 加固）— **风险最高，先做**

**为什么**：去掉 trust-all 后，若 `m.fengshows.com` 的证书链在设备上不被系统信任，凤凰台会直接取不到流。

**操作**：启动 → 打开选台面板 → 切到分组「港澳台」→ 选「凤凰卫视资讯台」

**看什么**：

| 结果 | 判定 |
|---|---|
| 正常出画面 | ✅ 通过 |
| 日志 `Request: ... url http://...` 且随后 `isPlaying` | ✅ 通过 |
| 日志 `auth request error javax.net.ssl.SSLHandshakeException` | ❌ 未通过 → 需对 `m.fengshows.com` 做最小豁免 |

> 若未通过：**只对该域名**加信任豁免，禁止恢复全局 trust-all。

### V3 两级探活（L4 生效）

**操作**：启动 → 等 20~60 秒 → 长按 OK 打开线路列表

**看什么**：

```powershell
adb logcat -d -s ChannelProbe:* | Select-String "probed|discard"
```

期望日志形如：

```
probed 62/62 lines, ok=41, verified=33
```

| 结果 | 判定 |
|---|---|
| `verified` > 0 | ✅ L4 验证生效 |
| 线路列表里同时出现 `1234ms` 和 `>1234ms` 两种文案 | ✅ 分级生效 |
| `verified=0` 且 `ok>0` | ⚠️ 降级了（分片都取不到），需查 `segment probe failed` 的原因 |
| `discard` | ⚠️ 被整轮丢弃，多为本机网络问题，换网络重测 |

**重点观察**：`ok` 与 `verified` 的差值 —— 差值大说明"能下载列表但拿不到分片"的线路多，这正是过去被漏判的一类。

| 结果 | 判定 |

## 二·补、线路实测画像（第二批）

### V11 真实来源回填（302 之后）

**为什么**：入口域名常常只是调度器。实测一个频道的 8 条线路来自 8 个域名，重定向后只有 4 台真实服务器。

**操作**：等探活跑完一轮（约 1 分钟），打开 CCTV-5 这类有 8+ 条线路的频道，看线路列表**最后一栏**。

| 结果 | 判定 |
|---|---|
| 多个**入口不同**的线路显示**相同**的真实 host | ✅ 识别成功——这正是过去看不见的情况 |
| 显示的是入口域名 | ⚠️ 该线路还没被探活过，再等一轮 |

确认探活确实跑过：

```powershell
adb logcat -d -s ChannelProbe:* | Select-String "probed"
```

### V12 实测画质

**操作**：线路列表里的「画质」标签。

| 结果 | 判定 |
|---|---|
| 标签由**实测分辨率**推导 | ✅ 生效 |
| 显示"未知画质"或名字里的数字 | ✅ 属正常回退，**不算失败** |

> **重要**：实测过的 Guovin CCTV 线路是**单码率 media playlist**，本身就没有 `RESOLUTION` 字段。
> 因此本项大面积走"名字推断"是**预期行为**，只有多码率源（master playlist）才有实测值。
> 判定标准是「没有变得更差」，不是「全部变成实测」。

| 播成功过的线路排到前面 | ✅ 排序生效 |
| 从没播过的线路没有被全部排到最后 | ✅ 中性 50 的处理生效 |

### V14 探活优先级 + 后台补探

**操作**：启动后连续快速切换分组 3~5 次（模拟"用户乱翻"），观察日志。

```powershell
adb logcat -d -s ChannelProbe:* | Select-String "probe queued|probe backlog|probed"
adb logcat -d -s MainFragment:*  | Select-String "probe backlog"
```

| 结果 | 判定 |
|---|---|
| 出现 `probe queued: N channels (pending=M)` | ✅ 待办累积生效（旧实现会覆盖，丢掉中间请求） |
| 出现 `probe backlog round 1/2/3: X channels` | ✅ 后台补探在工作 |
| 补探若干轮后，切到**没浏览过**的分组，"未探测"明显减少 | ✅ 目标达成 |
| `probe backlog` 只出现 ≤ 3 次 | ✅ 轮数上限生效（不会无休止发请求） |

> 注意：后台补探每轮间隔 60s，验证时需等待；不要因为"立刻没变化"就判失败。

### V15 换源优先选历史最优

**操作**：先正常使用若干次（让源健康统计积累），然后触发换源（把当前源改成明显不可用的地址，等到出现换源提示）。

| 结果 | 判定 |
|---|---|
| 日志形如 `rotate source 3/5 -> <URL> (score=100)` | ✅ 按分数选择 |
| 选中的源确实是成功率最高的那个 | ✅ 通过 |
| 所有源都没有成功记录时，退化为顺序轮换 | ✅ 属预期回退 |

### V16 线路裁剪（优中选优）

**操作**：清数据启动 → 等探活跑完（首轮 + 后台补探约 2 分钟）→ 打开任意频道的线路列表。

| 结果 | 判定 |
|---|---|
| 线路列表**不超过 6 条** | ✅ 裁剪生效 |
| 首轮 `probed` 的 `ok` 比例明显高于裁剪前（实测 38% → 64%） | ✅ 留下的都是优选线路 |
| 后续轮次出现 `probe skipped: N channels probed recently` | ✅ 已全覆盖，无遗漏 |

**实测记录**：`probed 200/200 (ok=128, verified=124)` → `probed 150/150 (ok=92, verified=80)` → 第 2 轮全部 `probed recently`。
即**总线路 350 条已全部探过**（裁剪前约 820 条，探不完）。

### V17 运行时动态重排（不再等下次启动）

**操作**：清数据启动（`probe.json` 为空）→ 观察日志。

```powershell
adb logcat -s TVViewModel:* ChannelProbe:*
```

| 结果 | 判定 |
|---|---|
| 探活 `probed` 之后 **1ms 内**出现 `resort lines: <频道> -> N lines, now playing #M` | ✅ 动态重排生效 |
| 重排后播放**没有中断**（画面继续，日志无新的 `switch`） | ✅ 索引保持正确 |
| 线路列表里**没有**"探测失败"的线路摆在可达线路之前 | ✅ 排序优先级修正生效 |

**实测记录**：

```
22:03:55.897  ChannelProbe: probed 200/200 lines, ok=134, verified=130
22:03:55.898  TVViewModel:  resort lines: CCTV-2 -> 6 lines, now playing #1
```

> 清数据是这一项的关键：此时 `probe.json` 为空，加载时所有线路都是"未探测"档，
> 因此**顺序只可能由动态重排改变**——这排除了"下次启动才生效"的可能。

**已知限制**：网段打散受可用来源数量约束。实测某频道 6 条线路只对应 4 个真实来源，
因此第 4 条起必然出现重复（物理上无更多来源可选），但**前 2 条（自动轮换范围）保证不同源**。

### 本轮重要发现（模拟器实测）

**F1. 排序与打散都依赖"上一次"的探活数据**

`diversifyLines` / `trimLines` 和线路排序都在 `TVList.finalize`（**加载时**）执行，而探活在加载**之后**。
所以首次安装（`probe.json` 为空）时：

- 打散退化为入口地址近似 → 同源线路挤在前面；
- 排序的 `sortKey` 全是"未探测"的中性值 → **探活结论根本没参与排序**。

实测对比：
- 第一次启动：线路 1/3/4 都是 `204.12.241.18`（同源相邻）；且一条 `探测失败` 的线路排在第 3 位（失败权重本应最高）
- **重启后**：线路 1~4 分别为 `204.12.241.18` / `192.187.115.106` / `69.197.146.178` / `74.91.26.218`

**结论**：整套"实测优选"在**第二次启动起**才完整生效。首次安装时排序依据很弱。

> 修复方向：探活在完成后对当前频道重排线路，并保持正在播放那条线路的索引不变。

**F2. 去掉 trust-all 让探活结论与实际播放一致**

实测中大量线路报 `Hostname zby.130519.xyz not verified`（证书主机名不匹配）→ 探活判失败。
过去 trust-all 的探活会把它们判为"可达"，但**实际播放用的是 media3 的系统校验**，本来就会失败。

所以这不是"误杀"，而是**探测终于和播放一致了**——过去是探活说谎。

**F3. 慢源的根因是 `raw.githubusercontent.com`，不是源本身**

`suxuang` 源在主机直连 raw 时实测 **25s**，而 App 内走 jsdelivr 只用 **2967ms**。
`/api/sources` 的 `via` 字段直接证实：3 个 GitHub 源全部命中 `cdn.jsdelivr.net`。

**F4. 单码率源拿不到实测分辨率（预期内）**

线路列表里多数仍是 `未知画质`——Guovin 这类源是单码率 media playlist，本身没有 `RESOLUTION` 字段。
V12 的真实收益要等多码率源才看得到；当前价值是"没有变差"。
