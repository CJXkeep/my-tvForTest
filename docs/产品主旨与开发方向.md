# 我的电视 · 产品主旨与开发方向

> **一句话**：一台给家人用的电视——打开就能看，坏了会自己想办法，实在不行才让人按一次 OK。
>
> **本文的定位**：这是**纲领文档（战略层）**，回答"做什么、为谁做、坚持什么、不做什么、怎么算成功"。

> **纲领的修改需要显式决策，不能顺手改**；战术文档随时可改。

## 一、我们到底在做什么

### 1.1 产品是什么

一个 Android TV 直播软件（单 module，Kotlin + Media3）。
它做三件事，按重要性排序：

1. **把分散的公开直播源整理成一份能用的频道表**（拉取 → 解析 → 去噪 → 同名折叠多线路 → 排序）。
2. **用尽量少的用户操作把它放出来**（遥控器 3 个键之内）。
3. **在"播不出来"时自己兜底**（换线路 → 换封装 → 降软解 → 换频道 → 换数据源），只在最后才提示人。

第 3 件事是本项目区别于普通播放器的**核心资产**，也是历次迭代投入最多的地方。

### 1.2 解决什么问题

现有电视直播 App 的典型毛病，正是我们要消掉的：

| 用户的痛 | 我们的答案 |
|---|---|
| 装完要填一堆订阅地址才会用 | **默认零配置**：装完即有台 |
| 某个台播不出来，一直转圈，只能干等 | **首帧看门狗**：15s 没画面就换下一条线，连续 2 次即判死 |
| 死台永远转圈，不知道该怎么办 | **统一终态出口**：停止转圈 + 说明原因 + 自动跳过 |
| 一个个试才知道哪条线好 | **线路探活 + 失败记忆**：坏的排后面，好的排前面 |
| 遥控器输入地址是灾难 | 复杂配置全部搬到**手机浏览器**（`ConfigServer`） |

### 1.3 目标用户 / 非目标用户

**目标用户（第一位）**：不会折腾的普通家庭用户，尤其是**老年人**——他们不会填地址、不会看日志、遇到黑屏只会反复按遥控器或放弃。
一切"是否需要用户理解某个概念"的取舍，都以此为准。

**次要用户**：愿意自己准备订阅源的进阶用户（提供远程配置入口即可，不为他增加界面复杂度）。

**非目标用户**：
- 想看付费/加密内容、期望"什么台都有"的用户（我们不做内容破解）。
- 想要多语言、皮肤、账号体系、频道管理的用户。

## 二、核心价值主张与成功标准

### 2.1 三句话价值主张

1. **装完就能看**——不填任何东西，首次启动就有台可播。
2. **坏了不用管**——绝大多数失败由程序自己消化，用户最多按一次 OK。
3. **界面就是画面**——不做首页、不用菜单树，电视就该是"一个画面 + 一条信息"。

### 2.2 北极星指标（可量化、每次迭代后复核）

| 指标 | 目标 | 当前（模拟器实测） | 出处 |
|---|---|---|---|
| 冷启动到起播 | **≤ 5s**（有缓存时 ≤ 1s） | 192ms（有缓存） | `性能审查.md` |
| 坏台自动离开耗时 | **≤ 20s** | 约 16s（12.3s 判定 + 4s 跳过） | `性能审查.md` |
| 死台无限等待 | **0**（必须收敛到终态） | 已修复 | `性能审查.md` A1~A5 |
| 列表滚动卡顿帧 | **0** | 0（297 帧） | `性能审查.md` |
| 首次安装所需配置步骤 | **0 步** | 0 | `整体审查.md` |
| 崩溃率 | **0**（无 `FATAL EXCEPTION`） | 模拟器 0；真机未验证 | 待真机 |

> **纪律**：以上任何指标在真机上未实测前，标记为"未验证"，**不得视为通过**（沿用 `迭代计划-体验与稳定性.md` 第八节的约定）。

## 三、不可动摇的设计原则

以下五条是历次迭代收敛出来的，任何新功能与它们冲突时**以原则为准**（当前版本较原表述更严格，新增第 5 条）。

| # | 原则 | 含义与推论 |
|---|---|---|
| 1 | **默认零配置可用** | 装完即有台。任何"必须配置才能用"的设计都不合格。 |
| 2 | **电视端只负责看** | 电视上只保留：上下换台、OK 开关列表、长按 OK 看线路、MENU 设置。输入字符、管理列表一律去远程页。 |
| 3 | **自动决策优于开关** | 软解、画质、换台方向、信息显示由程序判断。**设置项只会更少，不会更多**（当前 2 开关 + 4 按钮即上限）。 |
| 4 | **一切失败必须有终态** | 不允许存在"永远转圈/永远黑屏/静默无反馈"的路径。新加的异步链路必须回答："它失败时，用户看到什么？" |
| 5 | **工程预算投在成功率，不投在功能数** | 新增频道源、新增格式的价值，远低于"现有源多播成功 5%"。不堆功能、不堆概念、不堆设置项。 |

### 3.1 交互与视觉的一致性约定（现状）

- 深色底 + 绿色高亮（`#8BC34A`），面板/设置/线路列表必须是**同一套视觉语言**，禁止混用系统 `Switch`/`Button`/下划线 `EditText`（`迭代计划-体验与稳定性.md` 第十四节）。
- 播放中的状态提示**合并进信息条**，只有"需要用户做决定"时才出现全屏提示页（`ErrorFragment`）。
- 提示页的唯一按钮必须**自动获得焦点**（电视上弹窗按钮焦点不可控）。

## 四、边界：明确不做什么

> 这一节是**承诺**，不是建议。破坏边界的需求要单独立项讨论，不能顺手加。

### 4.1 功能边界

- **不做**：DIY 皮肤、多语言、账号体系、频道分组管理、自定义主题、播放记录、投屏、点播。
- **不堆**：设置项、弹窗、需要用户理解的新概念。
- **不引入**：需要维护的服务端、云账号、统计上报（崩溃日志只落本地 + 局域网导出）。

### 4.2 内容与合规边界（已决议，见第六节 D2）

原 `设计与迭代计划.md` 的表述是"不做绕过平台鉴权、付费墙、DRM 的逆向"。该表述**过严且不准确**，已按事实修正为三档：

| 档 | 内容 | 允许？ |
|---|---|---|
| 硬红线 | 破解 DRM、付费墙、订阅校验；抓取需登录的受保护内容 | **不做** |
| 灰色地带 | 调用平台**公开但未文档化**的 HTTP 接口取流（如凤凰 `m.fengshows.com/api/v3/hub/live/auth-url`） | **保留现状**：仅限个人自用，不公开分发、不上架、不商业化 |
| 正常 | 用户自带的订阅源、公开 IPTV 聚合源、用户自带 token/cookie 透传 | 支持 |

**结论**：保留凤凰平台适配。后续新增平台适配时，按同一档位评估并在此表登记。

### 5.3 需要澄清的三处（均已给出结论）

1. **凤凰卫视取流：属于"灰色地带"，不是"逆向"**
   `ApiClient.fUrl = "https://m.fengshows.com/"`，`FAuthService.getAuth()` 调 `api/v3/hub/live/auth-url`；
   `TVList.builtin()` 内置 3 个凤凰频道（硬编码 `pid`）。
   该接口是凤凰自家 H5 使用的公开接口，**未涉及 DRM / 付费墙 / 加密破解**，因此不构成"逆向"。
   结论：**保留**，仅限个人自用（见 4.2）。`jce/`、`proto/`、`requests/` 目录已空，说明重型实现此前已清理。

2. **trust-all 是独立技术债，修它不需要动适配**
   `ApiClient.getUnsafeOkHttpClient()` 与 `EpgStore.trustAllClient()` 都是全信任 + `hostnameVerifier{true}`。
   目标站点（`m.fengshows.com`、EPG 站点）均为正规 HTTPS，**并不需要**信任所有证书，属历史遗留的过度授权。

3. **白名单是硬规则，不是默认策略**
   `TVList.applyChannelFilter()` 只保留 CCTV + `endsWith("卫视")`；只有"过滤后一个不剩"才回退原样。
   对浏览大众用户这是对的，但会**静默丢掉**用户自带源里的地方台、港澳台等频道。
   D1 已定为 B（内置源聚合器），故**保持硬规则**；若将来切换到 A（自带源），这条必须改为可配置或分组保留。

### 5.4 文档自身的问题

- `整体审查.md` 与代码存在事实偏差：称"仅 1 处真 TODO、无注释代码"，实际 `MainActivity` 有 4 处注释代码块、`SP.kt` 有 TODO、多个死字段。
- 六份文档没有一份讲"为谁做、坚持什么、不做什么"——这正是本文补上的位置。

## 六、方向性决策（D1 / D2 / D3 均已定）

> 这些决策决定后续所有迭代的取舍。已决议项如需变更，必须显式回到本节改。

### D1：App 是"自带源的播放器"还是"内置源的开箱即用聚合器" —— **已决议：B（内置源聚合器）**

**决策**：保持选项 B——内置 5 个公开聚合源 + 凤凰台，装完即看（与原则 1「默认零配置可用」一致）。

**前提约束**（与功能无关，约束的是使用与分发方式）：
- 仅限**个人学习自用**，不公开分发、不上架应用商店、不商业化；
- 内容边界按 4.2 三档表执行；
- 若未来要面向公众分发，必须先切换到选项 A（不自带内容源）。

| 选项 | 含义 | 代价 |
|---|---|---|
| A. 播放器/聚合引擎 | 不内置内容源，默认源仅作示例 | 失去"装完即可用"；与原则 1 冲突 |
| **B. 内置源聚合器（已选）** | 内置 5 个公开聚合源 + 凤凰台 | 版权与合规风险由使用与分发方式决定 |

### D2：平台适配（凤凰卫视）的去留 —— **已决议：保留 + 加固**

**决策**：保留 `ApiClient` / `FAuth` / `FAuthService` / `FEPG` 与内置凤凰频道，**不做功能改动**。

理由：调用第三方公开接口取流属于灰色地带而非"逆向"（不涉 DRM / 付费墙 / 破解），适配本身不构成问题；
移除会损失 3 个频道与其 EPG，删除成本高于收益。

**随之执行的两项加固（与"去留"无关，属独立技术债）**：

| 项 | 动作 |
|---|---|
| `ApiClient.getUnsafeOkHttpClient()` | 改回系统信任链（保留 `enableTls12OnPreLollipop` 老设备兼容与 `DnsCache`），去掉 trust-all 与 `hostnameVerifier{true}` |
| `EpgStore.trustAllClient()` | 同样改为默认 `OkHttpClient` |

**风险提示**：去掉 trust-all 后，若某些老设备或 EPG 站点 TLS 握手失败，表现为该类频道取不到流——需真机回归确认；
届时只对**具体域名**做最小豁免，不得恢复全局 trust-all。

### D3：目标形态（TV-only 还是 TV + 手机） —— **已决议：TV-only**

- `AndroidManifest` 声明 `android.software.leanback required=true`，即**只面向 TV**。
- **决策**：明确 TV-only。触屏仅保证"能装能看"（`touchscreen required=false` 与双击/滑动分支保留），**不为其增加功能、不做手机版布局适配**。

## 七、方向路线（承接现有战术文档，收敛为三段）

> 以下是**方向**，不是任务清单；具体任务在 `迭代计划-体验与稳定性.md` 与 `设计与迭代计划.md` 中维护。

### 阶段 0：地基（**当前应优先**，先于任何新功能）

1. 方向已定（D1 / D2 / D3），按决议执行；后续变更须回到第六节显式改。
2. 建立最小可测基线：把解析、折叠、白名单、排序、健康判定抽成纯函数并加单元测试（当前 P0 债）。
3. 真机验证一轮，把 `测试计划.md` 中标"待真机"的项逐条落实。
4. 清理死代码（trust-all 已修复：`ApiClient` 与 `EpgStore` 已改回系统信任链）。

**验收**：能一条命令跑回归；真机跑通六条北极星指标；文档与代码无事实冲突。

### 阶段 1：成功率与秒开（**第一课题**，已有大量投入，继续）

- 数据源缓存、镜像、探活、排序已落地，重点是**在真实网络下量化收益**（`性能审查.md` E3：探活收益未量化）。
- **当前最大缺口：度量只到"HTTP 可达"（L3），没到"能播"（L4）/ "稳定播"（L5）**。方案见 `源可用性与质量专题.md`：
  两段式探活、端到端耗时排序、按 IP 网段去重。
- 拆分 `SourceManager`，让数据管线可测、可替换。

### 阶段 2：体验与工程收尾

- 提示收敛、引导合并、设置页保持减法。
- 播放链路拆 `PlaybackController`；按需启用 R8（先真机验证 keep 规则）。

### 明确暂不做

- 内置精选源（`设计与迭代计划.md` 待补项）——**取决于 D1**，在定位未定前不做。
- `SourceAdapter` 抽象——当前只有一个平台适配器，为单一实现引入接口属于过度设计；待第二个平台适配真正落地时再抽取（D2 已定保留凤凰适配）。
- 新的播放器/解码器引入——除非真机证明必要。

## 八、成功标准与验证纪律

1. **每次改动必须回答**：北极星指标哪一项变好了？没有变好的改动不进主干。
2. **没有真机验证的功能，不算完成**；模拟器只用于功能连通性，不用于手感/解码/长稳结论。
3. **不允许新增设置项**（原则 3）；确需新增，先在文档中论证并删除等量的旧设置项。
   2026-09-14 例外记录：新增「预加载下一频道」即按此执行——它是高风险实验功能（需两个解码器实例），
   必须让用户能关掉；同时删除了 `grid` / `guid` 两个死字段，设置项数量净减。
4. **不允许新增"无终态"的异步链路**（原则 4）。
5. **每次迭代结束更新本文第二节的指标表**，形成趋势，而不是只记"已完成"。
