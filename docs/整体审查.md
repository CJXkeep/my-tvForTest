## 二、现在的用户流程（这就是"现在是什么样的"）

### 启动（实测 192ms 到起播）
1. 读本地缓存 → 立刻渲染列表并起播（不阻塞等网络）
2. 后台并发拉取 **5 个数据源**（整体 12 秒截止），成功则原地重建列表并保持当前频道
3. 同时按"收藏 + 当前分组"做线路探活（后台，串行一轮）

### 频道与线路
- 白名单只保留 **CCTV + 卫视**（避免公开源里的杂项频道）
- 同名频道自动合并为多线路；线路顺序 = 探活延迟 + 真实播放失败记忆
- 线路列表显示：画质 · 探测状态（`950ms` / `探测失败` / `未探测` / `本机无 IPv6`）· 疑似录像 · 域名

### 遥控器操作
| 按键 | 行为 |
|---|---|
| 数字键 | 直选频道，支持 **1~4 位**（2 秒超时跳台） |
| 上 / 下 | 换台 |
| OK | 打开选台面板 |
| 长按 OK | 收藏 / 取消收藏（只本地重排，不打断播放） |
| 长按 ◀ / ▶ | 打开线路列表 |
| MENU | 设置页 |

### 失败自愈链（核心，全程尽量不要求用户操作）
```
首帧 15 秒没出来（看门狗）
  → 换下一条线路（静默无数据时）／换封装类型／软解降级（仅解码类错误）
  → 连续 2 次超时或线路试完 → 终态：停止转圈 + 停止播放器
  → 信息条提示 + 4 秒后自动跳下一个频道
  → 连续 3 个频道都不行 → 全屏提示"按 OK 换个数据源"，20 秒无操作自动换
  → 轮完 6 个候选源仍不行 → 提示"请检查网络或稍后再试"
```

### 数据源
- 内置 **5 个**公开聚合源；GitHub 地址**优先走 jsdelivr**，再回退原始地址与 ghproxy 系列
- 换源 = 一个按键（自动轮换候选源，不需要输入任何地址）

### 网络适配（本轮新增）
- 设备**没有 IPv6 出口**时：跳过 IPv6 线路（不探、不判、不记），列表里标明"本机无 IPv6"
- 探活整轮可达率 < 10% 视为本机网络问题，**丢弃该轮结果**（不把整表标死）

## 五、工程债与风险（按优先级）

| 优先级 | 项 | 影响 | 建议 |
|---|---|---|---|
| **高** | **零自动化测试** | 每轮改动只能靠模拟器手测，回归靠人眼 | 优先把纯逻辑抽成可测：M3U/TXT/JSON 解析、白名单与同名合并、线路排序、`Utils.hasIpv6`、`LineHealth` 判定。这几块恰恰是本轮改动最多、也最容易回归的地方 |
| **高** | 只验证过模拟器 | 遥控器/解码/长稳是电视端的核心体验 | 真机连续跑一周，重点看：长按手势、4K 硬解、连续换台 1 小时、待机唤醒 |
| 中 | 凤凰类频道鉴权重试 8 次、无退避、无提示 | 最坏约 80 秒静默（画面停在上一帧） | 加退避 + 第一次失败就提示"正在获取播放地址" |
| 中 | 大源扩展性：`loadRows` 一次性建 N 个 ViewModel + 3N 个观察者 | 当前无感；几千台会明显卡顿 | 按分组懒创建 |
| 中 | 两个"大文件"承载过多职责 | 改动风险集中，易互相影响 | 拆出 `SourceManager`（拉取/镜像/轮换/健康）与 `PlaybackController`（重试链/终态） |
| 低 | 探活的实际收益仍未量化 | 每次启动/切分组多一轮请求 | 观察真机收益；若不大，删掉 `probeScope` 调用即可（`LineHealth` 独立支撑排序） |
| 低 | 设置页在触屏设备上按钮不获焦 | 触屏模式特性，真机 TV 无影响 | 保持现状 |

## 七、一句话总评

功能面已经从"能播"走到"**坏了会自己想办法，实在不行才让用户按一次 OK**"；
主要短板不在功能，而在**验证方式**——零自动化测试 + 只在模拟器验证，
这两点是后续任何改动最大的风险来源。
