# 性能与稳定性审查

审查范围：播放链路、频道列表、启动路径、后台任务（探活 / 降权 / EPG）。
环境：MuMu 模拟器（720x1280，横屏 1280x720，density 240）。
所有结论都带代码位置或实测数据，**没有实测支撑的都标为"待验证"**。

> 换台 / 起播延迟的专项优化（起播时间线、预热与待命预加载、302 落点、重试耗时）见 `起播速度优化.md`。

## 二、卡死类问题（"一直在加载"的根因）

这一类问题的共同点：**流程没有终态**。用户看到的是永久转圈或黑屏，既没有错误，也没有下一步提示。

| # | 问题 | 证据 | 处理 |
|---|---|---|---|
| A1 | **重试上限被反复清零 → 死台无限重试** | `PlayerFragment.play()` 无条件调 `resetAttempts()`，而"自动换线"也会走 `play()`（`nextSource()` → `allReady()` → ready 观察者 → `play()`）。实测日志：`Source error` 每 3.3 秒一次、10+ 次不停，`isAttemptExhausted()` 永远为 false | [play()] 只在**频道 id 变化**时清零重试计数 |
| A2 | **没有错误回调的缓冲没有超时** | 加载只在 `STATE_READY/ENDED`、`onPlayerError`、`onIsPlayingChanged(true)` 时隐藏；"连通但不发数据"的线路（实测 CCTV-2 的一条线）**永远不产生 error** | 新增 **15s 首帧看门狗**：连续 2 次超时即进入终态 |
| A3 | **放弃后只弹一个会消失的 Toast** | `retryOnError()` 的最终分支只有 `Toast.makeText(...).show()`，转圈图标与黑屏留在屏幕上 | 新增 `enterTerminal()`：**隐藏加载 + 停掉播放器 + 统一出口** |
| A4 | **失败后用户不知道下一步** | — | `MainActivity.onChannelUnavailable()`：信息条说明原因 + 4 秒后自动跳过；**连续 5 个不可播就停下提示**（那通常是网络或数据源问题，继续跳没有意义） |
| A5 | **无线路时静默死路** | `TVViewModel.firstSource()` 的 else 分支只有 `Log.e`，不触发播放也没有任何反馈 | 补 `setErrInfo()` → 统一出口 |
| A6 | URL 去重把"不同频道同一个流"误判为重复 | `MainFragment.check()` 只比较 URL；源里不同频道共用同一个流很常见 | 去重**加上频道 id**，避免切台时静默不起播 |
| A7 | 凤凰类频道取流失败 | `Request` 失败 8 次后走 `onRequestFinished` → 错误页 | **已有终态**，本次不动 |

### 修复后的实测链路

```
19:25:13.732  MainFragment: switch CCTV-2 财经            ← 按数字键跳到死台
19:25:26.043  PlayerFragment: terminal: CCTV-2 财经 所有线路均不可用   ← 12.3 秒收敛
19:25:26.043  MainActivity:  unavailable 1: ...           ← 信息条提示 + 安排跳过
19:25:30.046  MainFragment: switch CCTV-3 综艺            ← 4 秒后自动跳过（已正常播放）
```

**重试策略也随之收敛**（这是"什么时候该放弃"的核心判断）：

- 静默无数据（看门狗超时）→ 说明**这条线本身是死的**，直接换下一条线路，不在原地换封装类型白等一个超时周期；
- 源/网络类错误（HTTP 4xx/5xx、连接重置、超时）→ **不做软解降级**（软解救不了网络），每条线路各试一次即判定不可用；
- 解码/渲染类错误 → 才降级软解重试一次（这才是软解能救的场景）。

## 三、崩溃风险

| # | 问题 | 位置 | 处理 |
|---|---|---|---|
| B1 | `onVideoSizeChanged` 除零 / 空引用 | `playerView?.measuredWidth?.div(playerView?.measuredHeight!!)`：该回调可能早于布局完成，此时 `measuredHeight == 0` → `ArithmeticException`（`playerView` 为空则 NPE） | 加空值与 0 值防护，改为浮点比较 |

## 四、性能问题（本次已修）

| # | 问题 | 说明 | 处理 |
|---|---|---|---|
| C1 | 列表**每绑定一行**都在分配集合 + 全量遍历节目单 | `MainFragment.channelDesc()` 里 `epg.value.filter{ it.beginTime < now }.last()`：一个频道可能有上百条节目单，逐行绑定时就逐行遍历 + 新建 List | EPG 已按开始时间排序，改为**倒序早退出**（通常 1~2 次比较即返回），零分配 |
| C2 | `isChannelDown` 每次调用都全表扫描 | `ChannelProbe.isChannelDown()` 里 `map.values.none { it.ok }`，而它在逐行绑定中被调用 | 结果更新时**预计算 `anyOk`**，判定退化为 O(该频道线路数) |
| C3 | 首次列表绑定触发主线程读盘 | `ChannelProbe` / `LineHealth` 的 `ensureLoaded()` 是懒加载，第一次被调用发生在列表绑定时（主线程） | 启动时在 **IO 协程里 `warmUp()`**，首屏绑定不再读盘 |

## 五、尚未处理（建议下一批，附判断依据）

| # | 项 | 现状与影响 | 建议 |
|---|---|---|---|
| E1 | `loadRows()` 一次性创建 N 个 `TVViewModel` + 3N 个 LiveData 观察者 | 当前白名单后只有 **79 台**，实测启动 192ms、滚动 0 卡顿，**无感**；换成几千台的大源会明显（估算 +50~100ms 与数 MB 内存） | 按分组懒创建；或把 EPG 从"每台一个 LiveData"改为从 `EpgStore` 直接查 |
| E2 | 列表刷新用 `notifyDataSetChanged()` | 行数少时无感；大源下会全量重绑可见行 | 换 `DiffUtil`，或按分组 `notifyItemRangeChanged`（已在探活刷新里这么做） |
| E3 | 探活范围 62 条 / 轮 | 已经是"当前分组 + 收藏"，仍在每次启动与切分组时发请求 | 观察真机实际收益；若价值不大，删掉 `probeScope` 调用即可——`LineHealth` 会独立支撑排序与"暂不可用"标记 |
| E4 | 大源下的内存增长 | 白名单过滤已把 2462 台压到 79 台 | 若用户坚持用大源，需 E1 一起做 |
| E5 | 凤凰类频道鉴权重试期间没有反馈 | `Request.fetchFAuth()` 最多重试 8 次且**无退避**，最坏 8 × HTTP 超时（约 80 秒）后才落到错误页；期间画面停在上一帧、无提示 | 重试加退避，或在第一次失败时就提示"正在重试获取播放地址" |

## 六、测量方法（可复用）

```powershell
# 冷启动时间线（onCreate → 起播）
adb logcat -s MainActivity:* MainFragment:* TVList:* PlayerFragment:*
#   onCreate 43.504 → use cached 43.586 → switch 43.696

# 列表滚动流畅度
adb shell dumpsys gfxinfo <pkg> reset     # 先清零
#   ...用方向键滚动列表...
adb shell dumpsys gfxinfo <pkg>           # 看 Total frames / Janky / p50~p99 / Missed Vsync

# 内存
adb shell dumpsys meminfo <pkg>

# 复现"一直加载"（修复前会永久转圈，现在约 16 秒切走）
#   找到列表里标"暂不可用"的频道，用数字键直接跳到它（例如 CCTV-2 财经 = 2）
#   观察三条日志：terminal → unavailable → switch
```

> 注意：模拟器是触屏设备，长按/焦点行为与真机不同；帧率数据也受宿主显卡影响，**结论以真机为准**。
