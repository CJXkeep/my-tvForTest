# 起播速度优化（换台 / 切线路）

> 回答一个问题：**从按下换台到画面出来，这段时间花在哪、有哪些能压下去**。
> 源码：`MainFragment`（换台与预热）、`PlayerFragment`（预加载 / 重试 / 观测）、`StreamPreheat`、`ResolvedUrl`。
> 环境：MuMu 模拟器（Android 12 / x86_64 / 横屏 1280x720）。**文中所有数字都是实测**，没有实测支撑的写在「待验证」。
> 相关文档：线路"选哪条、什么时候换"见 `线路选择与轮换机制.md`；本文只管"**多久出画面**"。

---

## 一、先让时间可观测（这一步是前提）

优化之前只有一句 `first frame in 3xxx ms`，看不出时间花在哪。现在 `PlayerFragment` 挂了
`AnalyticsListener`，起播阶段会打一条时间线（TAG `PlayerFragment`，格式 `[+偏移ms]`）：

| 日志 | 含义 |
|---|---|
| `load → <地址>` | 一次请求开始（播放列表 / 分片） |
| `done ← <地址> <字节数>` | 请求完成；`<地址>` 是**跳转之后的最终地址** |
| `fail ← <地址> <原因>` | 请求失败（含 HTTP 状态、连接重置等原文） |
| `cancel ← <地址>` | 请求被主动取消（切台 / 看门狗判死后的换线路） |
| `format <编码> <分辨率>` | 流格式已解析，接下来才是解码与渲染 |
| `first frame in Xms` | 首帧真正上屏 |

几个使用要点：

- 只输出**起播窗口**（`TRACE_WINDOW_MS = 10s`）内的 `load/done/format`，否则直播分片会刷屏；
  但 `fail` / `cancel` **不受窗口限制**——慢失败（例如 15 秒才被看门狗判死的那条）恰恰最需要知道原因。
- `cancel` 那一行别忽略：它表示"这条线路不是失败，而是被放弃了"，否则日志里会留下一段空白，看不出发生过什么。
- 计时基准与首帧统计**分开**（`traceBaseAt` / `playStartAt`）：首帧出来后前者仍继续，这样能看到**接管之后是否在立刻回补分片**。
- 另有一条 `standby: schedule in Xms (took over=…, flip=…)`：这是"预加载要等多久才开始"的实际档位，
  靠 `first frame` 到 `standby: prepare` 的时间差是**推不出来**的（中间叠着 `isPlaying` 的触发时机抖动）。

## 二、实测分解：瓶颈在网络，不在本地

换台到 CCTV-2 的完整时间线（优化前）：

```
[+31ms]    load  → 204.12.221.218:8181/3m1080p/cctv2.m3u8
[+1795ms]  load  → 204.12.241.18:82/live/cctv2md/segment_28114.ts
[+1796ms]  done  ← 204.12.241.18:82/live/cctv2md.m3u8  210B      ← 跨 host(8181→82) = 302 跳转
[+3430ms]  format video/avc 1280x720
[+3463ms]  first frame
```

| 阶段 | 耗时 | 占比 |
|---|---|---|
| m3u8 请求（含 302 跳转） | 1764ms | 51% |
| 首分片 → 流格式确定 | 1635ms | 47% |
| 解码器 → 渲染 | **33ms** | **1%** |

**结论：本地侧只占 1%。** 这条结论有很强的排他性——它直接说明调缓冲阈值、
调解码器参数、换渲染策略都不可能改善启动首帧，因为那些不是瓶颈所在。

另一条同源的观察：CCTV-1 首帧 2161ms，但那个分片（1.99MB）要到 `[+6800ms]` 才下载完。
`BUFFER_FOR_PLAYBACK_MS = 500` 让画面在分片没下完时就出来了，这是首帧不算更慢的原因。

## 三、已做的优化

按"证据 → 处理 → 实测效果"列：

| # | 问题 | 证据 | 处理 | 实测效果 |
|---|---|---|---|---|
| 1 | 来回翻台（上一个/下一个交替）时，待命播放器被备成**下一个相邻台**，用户按回去必然落空 | 折回时 `preloadOffset` 翻转，待命不匹配 → 每次整段重载 | `PlayerFragment.flipFlop`：按回"上一次换台前的台"时，预加载目标改为**刚离开的那个台** | 折回首帧 **2313 / 2427ms → 24~68ms** |
| 2 | 连按换台时每次按键都预热，中间台的握手纯属白做，却在后台积压成串请求 | 20 次连按 → **17 次提交 / 21 个任务 / 约 8.4 秒**才消化完，而用户 1.5 秒就停手了 | 预热从"每次按键"移到**去抖触发后**（位置已稳定） | 同样 20 次连按 → **1 次提交 / 4 个任务** |
| 3 | 折回且未命中接管时，仍按常规 1500ms 才准备待命 | 待命就绪 = 延迟 + 加载，实测 **0.6~4.7s**（取决于该台近期是否被访问过），用户按快一点就吃不到 | 新增 `PRELOAD_DELAY_FLIP_FLOP_MS = 600`：折回的目标是"刚播过"的台，流是热的 | 就绪窗口约 **4s → 3s** |
| 4 | 待命加载失败后，`onIsPlayingChanged` 再次排程会**原样重建**同一个死台 | `failed` 之后 124ms 又 `prepare` 同一个连不上的台 | 失败频道进黑名单（`STANDBY_FAILED_TTL_MS = 5min`），用户真正切过去时清除 | 日志出现 `standby: skip #82 (failed recently)`，不再白等一次连接超时 |
| 5 | 加载层对"当场就返回"的失败仍退避重试 3 次 | 死线路 `Connection reset` 在 41ms 就失败，却白等 **3.4 秒**才换线路；与 `retryOnError` 里"源类错误多试只是让用户多等"的判断自相矛盾 | 自定义 `LoadErrorHandlingPolicy`：**第二次同类确定性失败**直接放弃（`C.TIME_UNSET`），超时不算 | 失败到换线路 **3.4s → 50ms**（同一条死线路的直接对照）。整台判死实测约 15s，其中这条线路的退避原本就占 3.4s |
| 6 | 每次起播都走一遍 302 跳转 | m3u8 阶段 1.76s 里有**一整轮往返**是跳转 | `ResolvedUrl`：预热时通过 `getUri()` 读回跳转落点，播放直接请求落点 | m3u8 阶段 **1764ms → 1021ms** |
| 7 | 落点只由预热记录，而预热**不含当前台**，所以"启动后第一个台""刚切过去的台"仍走跳转 | 同一条线路两次实测：走原始 746ms、走落点 265ms | 播放时在第一个响应回来后也记录落点 | 同一条线路首帧 **2229ms → 874ms** |
| 8 | 待命播放器沿用主播放器的 10s 缓冲水位，就绪后仍继续多拉约 7 秒直播数据 | 而频繁翻台时每次翻转都要释放它、为下一个台重拉 | 待命用独立水位 `STANDBY_MIN/MAX_BUFFER_MS = 5s / 10s` | 每次预加载少下约 5 秒数据；40 秒观测无卡顿 |
| 9 | 预热只防"同地址重复"，防不住"地址各不相同"的洪流 | 连按换台每次提交的都是新地址，`inFlight` 只增不减 | `MAX_IN_FLIGHT = 8` 兜底 + `MAX_TARGETS` 4→5（容下"最近邻居的第二条候选线路"） | 队列有上界；多预热的一条正是自动轮换的下一个目标 |

> 第 2、3 项要一起看：**预热负责握手，待命负责整段缓冲**，两者都不该在"位置还没稳定"时做。

## 四、常量速查

| 常量 | 值 | 位置 | 作用 |
|---|---|---|---|
| `SWITCH_DEBOUNCE_MS` | 150 | `MainFragment` | 换台去抖：停手这么久才真正起播 |
| `PRELOAD_DELAY_MS` | 1500 | `PlayerFragment` | 常规起播后多久准备待命 |
| `PRELOAD_DELAY_AFTER_PROMOTE_MS` | 300 | `PlayerFragment` | 接管后（画面来自已缓冲的流） |
| `PRELOAD_DELAY_FLIP_FLOP_MS` | 600 | `PlayerFragment` | 折回未接管时（目标是刚播过的台） |
| `STANDBY_FAILED_TTL_MS` | 300000 | `PlayerFragment` | 待命失败静默期 |
| `STANDBY_MIN/MAX_BUFFER_MS` | 5000 / 10000 | `PlayerFragment` | 待命专用缓冲水位 |
| `MIN/MAX_BUFFER_MS` | 10000 / 30000 | `PlayerFragment` | 主播放器缓冲水位 |
| `BUFFER_FOR_PLAYBACK_MS` | 500 | `PlayerFragment` | 首帧起播阈值（默认 2500） |
| `TRACE_WINDOW_MS` | 10000 | `PlayerFragment` | 时间线输出窗口 |
| `MAX_TARGETS` / `CONCURRENCY` | 5 / 2 | `StreamPreheat` | 单轮预热上限 / 并发 |
| `COOLDOWN_MS` / `MAX_IN_FLIGHT` | 60000 / 8 | `StreamPreheat` | 同地址冷却 / 在途上限 |
| `MAX_ENTRIES` | 128 | `ResolvedUrl` | 落点条目上限 |

## 五、已知取舍

1. **`flipFlop` 猜错方向会多建一次待命播放器。** 折回后若继续同向连按，那个"刚离开的台"就白备了。
   代价与改动前方向的固定代价同级，且解码器数量上限仍是 2（`promoteStandby` 里旧播放器立刻释放）。
2. **待命缓冲水位 5s 让接管瞬间的抗抖动余量变浅。** 接管后主播放器才按 10s 水位补回来，
   风险窗口是"刚出画的头几秒"。所以没有按最初设想的压到 3s。
3. **确定性失败不重试降低了瞬时抖动容忍度。** 缓解办法是"只拦第二次"——第一次仍走默认快速重试。
4. **落点可能带时效参数**（实测见过 `?RTS=<时间戳>`、`?auth=test20251009`）。所以缓存是尽力而为的：
   播放走落点失败 → `forget` 并退回原始地址重试一次（不计入重试次数）；预热走落点失败 → 同样 `forget`。
5. **预热最近邻居的第二条线路，每轮多一个请求。** 播放列表只有几百字节，且这条线路正是自动轮换的下一个目标。

## 六、被否掉的方案（避免重复投入）

| 方案 | 否掉的原因 |
|---|---|
| **多线路并行 race**（并行起播、取首个出画） | 需要 3 个解码器实例，而代码里对第二个待命播放器已有注释："个别电视盒子连第二个实例都分配不到硬件解码器"。 |
| **让排序"耗时优先于探活档位"** | 参见下一节：实测证明"线路间 2.7 倍差异"几乎全来自**是否走落点**，不是线路本身；都走落点时两条线路只差约 300ms（在波动范围内）。为这点差距放弃"先保证能播"不划算。 |
| **双待命播放器（上、下各一个）** | 同上，3 个解码器实例的风险大于收益。 |
| **本地调参改善启动首帧**（缓冲 / 解码 / 渲染） | 见第二节：本地侧只占 1%。 |
| **预热第 2、3 条线路来"选快的"** | 预热的每条线路只读播放列表，最多给到 `LEVEL_REACHABLE`；而排序里已验证到分片的线路是 `LEVEL_SEGMENT`，**永远优先**——这条路根本不会改变排序结果。 |

## 七、一个容易看反的现象：线路快慢

同一频道（CCTV-1）三条线路，m3u8 阶段 / 首帧：

| 线路 | 走原始地址（含跳转） | 走落点 |
|---|---|---|
| `74.91.26.218:82/live/cctv1hd.m3u8` | — | **241 / 234ms**　→　1131 / **586ms** |
| `204.12.221.218:8181/3m1080p/cctv1.m3u8` | 746ms　→　2229ms | **265ms**　→　**874ms** |
| `38.75.136.137:98/gslb/…?auth=test20251009` | 1893ms　→　3284ms | — |
| `63.141.230.178:82/gslb/zbdq5.m3u8?id=cctv1hd` | 2457ms　→　4432ms | — |

两个结论：

1. **同一线路的重复测量是稳定的**（241 / 234ms），说明这套测量可信，差异不是噪声。
2. **看起来的"线路差异"主要来自跳转**：同一条 `3m1080p` 线路，走原始地址首帧 2229ms，
   走落点 874ms。所以"哪条线路快"在**落点都记好之后**才是个有意义的问题——而那时差异只剩三百毫秒量级。

> 注意排序里**慢的线路排在前面往往是有意的**：`probeLevelRank` 让"已验证到分片"优先于"仅可达 / 未探测"，
> 即用确定性换速度。看到"慢线路被选中"时先确认它的探活档位，不要直接当成 bug。

## 八、待验证（真机）

模拟器无法反映真实盒子的解码器与带宽约束，以下几项必须在真机上确认：

- [ ] **待命缓冲水位 5s**：窄带宽设备上接管后是否更早进入卡顿（重点看 `onRebuffer` 日志与降画质提示）。
- [ ] **三档预加载延迟 300 / 600 / 1500ms**：真机连按节奏是否与模拟器不同，是否需要调整分档。
- [ ] **`MIN_BUFFER_MS = 10s`**：直播维持 10 秒水位在窄带宽下是否值得（它同时影响抗抖动与带宽占用）。
- [ ] **落点回退路径**：需要构造"落点已过期"才能触发，目前只有逻辑审查 + 确认它不影响正常路径。
- [ ] **确定性失败不重试**：真机上"瞬时 reset 后第二次成功"的比例（若偏高，说明该策略过于激进）。
